# v3.0 — 공동 작업 백엔드 (Firestore)

행사 관리는 혼자 하는 일이 아니다. 사무국·PCO·리에종·여행사·재무가 같은 데이터를 보고
각자 자기 영역을 고쳐야 한다. 그래서 저장 구조를 "브라우저 로컬"에서 **공유 백엔드**로 바꿨다.

---

## 1. 무엇을 골랐고 왜인가

| 선택지 | 판단 |
|---|---|
| **Firestore + Firebase Auth** ← 채택 | 서버를 운영할 필요가 없고, 변경이 실시간으로 모든 화면에 반영되며, 이미 쓰는 구글 클라우드 프로젝트 안에서 끝난다. 규모(담당자 10여 명, 문서 수천 건)에서 무료 한도 안쪽이다. |
| Cloud SQL + API 서버 | API 서버를 직접 만들고 운영해야 하고, 실시간 반영을 따로 구현해야 한다. 이 규모에서는 과하다. |
| 구글 시트 | 동시 편집은 되지만 권한을 항목별로 나눌 수 없고, 검증·이력·알림을 붙이기 어렵다. |

## 2. 구조

```
화면(React)
   │  dispatch(action)
   ▼
mutations.ts    액션 → 문서 변경 목록(Mutation[])
   │
   ├─ LocalBackend     : 브라우저 localStorage (1인·데모·단일 HTML)
   └─ FirebaseBackend  : Firestore 문서 쓰기 + onSnapshot 실시간 구독
```

핵심은 **상태를 통째로 저장하지 않는다**는 점이다. 연자 한 명, 업무 하나가 각각 문서이므로
두 사람이 서로 다른 연자를 동시에 고쳐도 서로를 덮어쓰지 않는다.

같은 Mutation 구조를 두 백엔드가 공유하므로 로컬 모드와 공유 모드의 동작이 갈리지 않는다.
설정(`config.json`)이 있으면 공유 모드, 없으면 로컬 모드로 **자동 전환**된다.

### 컬렉션

`members` `conferences` `sessions` `speakers` `supportPackages` `tasks` `communications`
`mailTemplates` `checklistTemplates` `auditLogs` `creditPrograms` `abstracts` `registrations`
`sponsors` `docs` `docTemplates` `comments` `attachments` + `memberInvites` `presence`

## 3. 권한 — 역할별로 고칠 수 있는 영역이 다르다

`firestore.rules` 에 규칙으로 못 박았다. 화면에서 가리는 수준이 아니라 **서버가 거부**한다.

| 역할 | 쓸 수 있는 범위 |
|---|---|
| 사무국 | 전체 (구성원 초대·행사 설정 포함) |
| PCO | 행사·세션·연자·업무·제출물·초록·등록 |
| 리에종 | 담당 연자·업무·커뮤니케이션·문서·코멘트 |
| 여행사 | 연자 문서 중 **항공·숙박·배차 필드만** |
| 재무 | 연자 문서 중 **정산 필드만**, 등록·후원 |
| 연사 | 읽기 전용(초대 시) |

- 변경 이력(`auditLogs`)은 **생성만 가능**하고 수정·삭제할 수 없다.
- 초대받지 않은 계정은 어떤 문서도 읽을 수 없다.

### 초대 흐름

1. 사무국이 이메일로 초대장(`memberInvites/{email}`)을 만든다.
2. 해당 구글 계정으로 처음 로그인하면, 초대장에 적힌 **역할 그대로** 본인 멤버 문서가 생성된다.
3. 초대장에 없는 역할로는 승격할 수 없다(규칙에서 차단).

## 4. 검증

`npm run test:rules` — Firestore 에뮬레이터에서 19개 항목을 확인한다.

```
✓ 로그인하지 않은 접근은 차단된다
✓ 초대받지 않은 계정은 연자를 읽을 수 없다
✓ 여행사는 교통·숙박을 수정할 수 있다 / 사례비는 수정할 수 없다
✓ 재무는 정산을 수정할 수 있다 / 항공은 수정할 수 없다
✓ 변경 이력은 수정·삭제할 수 없다
✓ 초대장에 없는 역할로는 승격할 수 없다
✓ 한 담당자의 수정이 다른 담당자 화면에 실시간 반영된다
… 19/19 통과
```

## 5. 아직 남은 것

- **동시 편집 충돌**: 같은 연자의 같은 항목(예: 제출물 목록)을 두 사람이 동시에 고치면
  나중 저장이 이긴다. 연자·업무 단위로는 분리되어 있어 실제 충돌 가능성은 낮지만,
  제출물·동반자처럼 문서 안의 배열은 필요하면 하위 컬렉션으로 더 쪼갤 수 있다.
- **알림**: 변경 시 메일·슬랙 알림은 아직 없다. Cloud Functions 로 `auditLogs` 생성을
  구독해 보내는 방식이 자연스럽다.
- **첨부 파일 실물**: 현재는 보관 위치만 기록한다. Cloud Storage 연동이 다음 단계다.
- **오프라인**: Firestore 가 로컬 캐시에 변경을 쌓아 두므로 잠깐 끊겨도 입력은 유지되고,
  연결되면 자동 반영된다. 다만 장시간 오프라인 사용은 검증하지 않았다.
